# Firebase notification setup

Researched 2026-10-16 against the repository and the official sources below. No Firebase project, credentials, dependency, Railway variable or deployment was changed. This is a setup and integration proposal, not working push delivery.

## Agreed behavior

- Dispatcher chat reaches every approved signed-in installation, including with shift and GPS off. Notifications include message content, subject to Android's lock-screen privacy settings.
- Visible chat receives the live message silently. Orders, Map and Profile receive an alert. Background and locked phones should receive alerts without an open Vue screen.
- Reading syncs across devices. Logout, device revocation and account blocking stop delivery to the affected installations.
- One control in Profile enables or mutes notifications. Denying notifications does not block starting or continuing a shift.
- Swiping away the app must keep a running shift. Explicit Offline ends it. The new connection policy retries for 60 seconds, then ends availability if recovery fails; assigned trips remain assigned.
- Public orders are immediately visible and claimable in every region. Only drivers in the order's region get the 20-second popup. Private offers remain exclusive for 20 seconds, then become public only with dispatcher fallback enabled.

These are product requirements. FCM transports alerts; it does not determine shift ownership, order visibility, claim eligibility or a successful acceptance.

## What exists today

The checked source uses Capacitor Android 6.2.1, Android Gradle Plugin 8.2.1, compile SDK 35, target SDK 34 and minimum SDK 22. `android/app/build.gradle` declares release application ID `io.openride.driver`, with `.test` appended for debug. `capacitor.config.json` declares the base ID. Debug Firebase registration must therefore use **`io.openride.driver.test`**, not the base ID.

There is currently no Firebase Messaging dependency, Google services plugin or `FirebaseMessagingService` in the Android manifest. The native `ShiftService` fetches notification events through `/native-shift/tick`, which ties them to GPS/shift operation. Its `onTaskRemoved()` explicitly ends the shift. Both behaviors need code changes to meet the new requirements.

The backend's existing `Driver.pushToken` is one token per driver. It cannot represent all approved signed-in installations. Push registrations need to be bound to the authenticated installation and environment instead.

## Owner setup

1. Open the [Firebase console](https://console.firebase.google.com/) under the business-owned Google account. Create a test project, for example `Tayyn Hyzmat Test`. Google Analytics is optional; Firebase Authentication, Firestore and Realtime Database are not needed for FCM transport. Our accounts, messages and business logic stay on Railway. Use a separate production project when production is provisioned. This separation is a project recommendation. [Android setup](https://firebase.google.com/docs/android/setup), [FCM server environment](https://firebase.google.com/docs/cloud-messaging/server-environment)
2. In Project settings → General → Your apps, add an Android app with package **`io.openride.driver.test`**. Download its `google-services.json`. When preparing the release app, register **`io.openride.driver`** in the appropriate production Firebase project and download that app's configuration. Package names are case-sensitive and cannot be changed on an existing Firebase Android registration. The basic FCM setup does not require a SHA certificate fingerprint; add fingerprints only if a subsequently selected Firebase product requires them. [Android setup](https://firebase.google.com/docs/android/setup), [FCM Android client](https://firebase.google.com/docs/cloud-messaging/android/client)
3. Supply the test config locally as `android/app/src/debug/google-services.json` and the production config as `android/app/src/release/google-services.json`. Variant-specific paths are supported by the Google services plugin. The file must contain a client whose Android package matches the built variant. These files contain app/project identifiers, not a server private key. This project keeps environment configs out of commits and supplies them through local/CI configuration so a test APK cannot accidentally use production. The checked-in `.gitignore` covers these paths; build injection and plugin integration are still pending. [Google services plugin](https://developers.google.com/android/guides/google-services-plugin)
4. Project settings → Cloud Messaging: verify **Firebase Cloud Messaging API V1** is enabled. If it is disabled, follow its Google Cloud API link and enable `fcm.googleapis.com` for the same project. We should use the Admin SDK or HTTP v1, not the retired legacy server-key API. [Server environment](https://firebase.google.com/docs/cloud-messaging/server-environment), [HTTP v1 authentication](https://firebase.google.com/docs/cloud-messaging/auth-server)
5. Create a dedicated sender service account in the same Google Cloud project. Grant **Firebase Cloud Messaging API Admin**, IAM role **`roles/firebasecloudmessaging.admin`**, rather than project Owner/Editor. This role includes `cloudmessaging.messages.create`. Generate one JSON private key for the Railway sender, or use a supported keyless identity integration if provisioned separately. Do not put this JSON into the APK, `google-services.json`, Git or chat. [Firebase IAM roles](https://firebase.google.com/docs/projects/iam/roles-predefined-product), [HTTP v1 authentication](https://firebase.google.com/docs/cloud-messaging/auth-server)
6. Put the service-account credential in the matching Railway **backend service and environment only**. Proposed integration variable `FIREBASE_SERVICE_ACCOUNT_JSON` would hold its JSON and be read by the backend Admin SDK adapter. This variable is not implemented yet. Alternatively, a securely mounted JSON file can be referenced by `GOOGLE_APPLICATION_CREDENTIALS`; that variable expects a file path, not the JSON body. Never use a `VITE_` variable or expose the credential through frontend configuration. Configure test and production credentials separately. [HTTP v1 authentication](https://firebase.google.com/docs/cloud-messaging/auth-server)
7. After the native and backend work below, rebuild and install the APK, open it at least once and allow notifications in Profile. Android 13+ requires runtime `POST_NOTIFICATIONS` permission. Confirm Google Play services are installed and compatible on the actual Infinix and use a Google Play/Google APIs emulator image. Phone model, Android version and Wi-Fi alone do not establish FCM availability. [FCM Android client](https://firebase.google.com/docs/cloud-messaging/android/client), [Android setup](https://firebase.google.com/docs/android/setup)

## Native integration still required

Add the Google services Gradle classpath to the existing root `buildscript.dependencies`, apply `com.google.gms.google-services` in the app module and add a pinned Firebase Messaging dependency. The official plugin guide currently shows Google services 4.5.0. Do not copy a latest Firebase BoM without checking compatibility: this app has minSdk 22; Messaging 25 raises that minimum to 23 and Messaging 26 to 24. Choose and test the SDK/toolchain combination explicitly or approve an Android minimum-version change. No minimum-version change is authorized by this research. [Plugin guide](https://developers.google.com/android/guides/google-services-plugin), [Firebase Android release notes](https://firebase.google.com/support/release-notes/android)

Implement a native `FirebaseMessagingService` and native persisted notification coordinator. Vue alone cannot process messages after its WebView is gone. Capacitor 6's official plugin documentation explicitly says `pushNotificationReceived` is not called for data-only notifications when the app has been killed, and recommends a custom native service for this case. Avoid two separately registered messaging services competing for events. [Capacitor 6 push plugin source](https://github.com/ionic-team/capacitor-plugins/blob/6.x/push-notifications/README.md)

The payload choice matters:

| Payload                                | Foreground                 | Background                                                                               | Consequence here                                                                                                    |
| -------------------------------------- | -------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `notification`, optionally with `data` | Native `onMessageReceived` | SDK displays the system notification; accompanying data reaches the launch intent on tap | Simple visible delivery, but application deduplication and stale-offer checks cannot run before background display. |
| Data-only                              | Native `onMessageReceived` | Native `onMessageReceived`, subject to Android/FCM delivery limits                       | App controls visibility, expiry, duplicate suppression, content and notification taps. Requires native handling.    |

Source: [Receive messages on Android](https://firebase.google.com/docs/cloud-messaging/android/receive).

Recommend data-only events routed through the same native coordinator as Socket.IO alerts. Include a stable application event ID, event kind, message/order ID, server timestamp, expiry and required display text. Include enough text to render promptly without waiting for another network request. A chat notification should say `Сообщение диспетчера` and show the message preview. Tap opens the authenticated chat; it never accepts an order. FCM transport is encrypted but not end-to-end encrypted, so Google receives the preview as delivery data. Do not include customer phones or other unnecessary order data. [Message types](https://firebase.google.com/docs/cloud-messaging/customize-messages/set-message-type), [Android message priority](https://firebase.google.com/docs/cloud-messaging/android/message-priority)

Use high priority only for timely, user-visible alerts with notifications enabled. Repeated high-priority messages without visible notifications can be deprioritized. A muted installation or currently visible chat should use the live socket/read sync rather than silent high-priority pushes. Notification channels and user permission still govern whether an alert is visible or audible. One app control cannot override a channel muted in Android Settings. [Message priority](https://firebase.google.com/docs/cloud-messaging/android/message-priority), [Android client](https://firebase.google.com/docs/cloud-messaging/android/client)

## Delivery, security and duplicate prevention

These are proposed implementation rules, not Firebase guarantees:

- Persist the message first and enqueue delivery after commit. Sending a push must never be the transaction that creates the message or claims an order.
- Register installation addresses through authenticated endpoints, bound to driver, approved device and environment. Refresh the address on native registration changes and app startup. The pinned SDK determines the supported registration API. Current docs expose legacy `getToken`/`onNewToken`; newer release notes introduce installation-based registration, so do not mix SDK generations. Remove invalid destinations and revoke bindings on logout, blocked/deactivated accounts or device revocation. [Registration management](https://firebase.google.com/docs/cloud-messaging/manage-tokens), [Release notes](https://firebase.google.com/support/release-notes/android)
- Fan out to every approved signed-in device, not only the shift owner. Shift control remains exclusive. Do not use a publicly subscribable topic for private driver chat.
- Prefer Socket.IO when a device confirms receipt. Use FCM as delivery fallback when the device is backgrounded or realtime acknowledgement is missing. The server cannot reliably identify a device as "fully closed". A per-device persistent event ID ledger suppresses Socket.IO/FCM/native-poll overlap.
- Remove chat delivery from the GPS-dependent tick path once FCM delivery exists. Keep one notification renderer. Reconnecting the socket must fetch missed messages and current order state, not replay every historical alert.
- Persist native foreground/chat visibility with lifecycle updates. Suppress alerts only while the correct authenticated chat is genuinely visible. On other screens, alert and preserve navigation. Sync read state and clear matching delivered notifications across devices on the next reachable update. Already heard sounds cannot be recalled.
- Give orders a short transport TTL bounded by the offer deadline and recheck expiry/current ownership before showing controls. A stale FCM event must never reopen a claimed, cancelled or expired private offer. TTL zero drops a message that cannot be delivered immediately; a short TTL is still no delivery deadline guarantee. First successful server claim wins. [Message lifespan](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan)
- Keep native shift location tracking independent of notification delivery. Removing `onTaskRemoved()` termination and testing service lifetime are necessary for the newly requested swipe behavior. FCM cannot substitute for continuous GPS or maintain shift eligibility by itself.

## Limits and acceptance checks

FCM cannot guarantee a private offer reaches a phone within 20 seconds. Doze, network reachability, Google Play services, user permission and manufacturer battery controls affect delivery. It is also not a guarantee after a swipe on every manufacturer. Android Settings → Force stop requires reopening before messaging resumes. Messages remain in our database and must catch up after reconnection. [Android priority](https://firebase.google.com/docs/cloud-messaging/android/message-priority), [FCM force-quit prerequisite](https://firebase.google.com/docs/cloud-messaging/flutter/receive)

Before release, use isolated accounts and test the real Infinix Android 14 on its actual Wi-Fi and mobile networks, including VPN conditions. Cover visible chat versus each other screen, shift/GPS off, locked screen, swipe away, Doze, permission denied, notification mute, two approved devices, read sync, logout/revocation, duplicate arrival, missed connection, stale private offer and another driver's claim. Verify swipe preserves the shift, a failed 60-second reconnect ends availability, and Force stop does not leave a falsely available driver. These are required checks; none were performed by this research.
