# Driver addresses and provider limits

GPS coordinates and saved active region polygons determine a driver's operating region. An address is optional display information. Geocoder configuration, quota exhaustion and provider failures never gate GPS reporting, Online, order browsing or an accepted trip. Outside every polygon, show `Вне районов` and the actual coordinates. Never substitute a nearest centre or a provider administrative area.

## Lookup policy

Only the driver app requests address labels. Before a shift, a signed-in phone may make one convenience lookup once fresh precise GPS, internet and the visible home-screen location view are available. Its point is transient: it does not update the driver's saved tracking position, dispatcher map or operating region. The installation's completed attempt is remembered by the server, so reload, relaunch, reconnect and another login do not repeat it. The shared driver cooldown still prevents rapid requests across phones.

After an explicit Online action succeeds and that phone owns the shift, it requests a fresh address again. The first on-shift lookup may bypass the five-minute wait left by the convenience lookup once. It still obeys the fleet budget and provider backoff. Repeated Online taps, toggling a shift, new sessions and new devices cannot repeatedly bypass the limit. The server records whether the last attempt was off shift or on shift alongside the per-installation convenience marker.

During a shift, the visible home-screen location view refresh automatically no more than once every five minutes per driver, without a movement requirement. The native background GPS service never requests an address. Hidden/background views pause address requests. Returning to the foreground or reconnecting makes one catch-up request only if due; it never replays missed intervals. A manual refresh uses the same persisted limit and disables while pending or waiting for the server's retry time. Only the shift-owning installation may request an on-shift label. Dispatchers neither request nor display address labels; their map and details use GPS coordinates, saved region and position age.

On-shift requests use fresh saved GPS. The separate off-shift request accepts only a fresh, validated local point for reverse geocoding and does not upload it as tracking data. Stale or unusable GPS produces coordinate fallback rather than a provider call. Both request modes are optional and never delay or gate Online, claims or trip controls.

PostgreSQL serializes reservations before any outbound request. Every attempted provider call, including errors and timeouts, consumes the budget. Cancelling a browser request does not refund an attempted call. The fleet ceiling is `floor(confirmed daily limit × 0.8)`. The remaining 20% is unused reserve. This application counter cannot account for other applications, API keys or SDK consumers sharing the vendor account. Configure its confirmed allocation accordingly and monitor the provider's own account usage.

Provider calls use the private Yandex HTTP Geocoder adapter with longitude first, a four-second timeout and short component labels. There is no public Nominatim fallback. Failures open a shared persisted backoff of 30 seconds, doubling to five minutes after repeated failures. HTTP 403 opens a one-hour breaker. Already in-flight requests can finish; later reservations respect the breaker. Success cannot erase a newer concurrent failure.

The short label uses a street and house first, then the most specific district and house, then a street alone, then the most specific district alone. Yandex lists components from broadest to most specific, so the last district wins. For example, a house response with no street can show `микрорайон Парахат 7/3, 14`; a district response can show `квартал Кёши`. A city, province or country alone produces no label and the driver sees coordinates. These names never determine the driver's saved dispatch region.

## Server configuration

These variables belong only in the API service. Never add the private credential to Vite variables, web Docker build arguments or the APK. The public Maps JavaScript credential remains separate.

| Variable | Meaning |
| --- | --- |
| `YANDEX_GEOCODER_API_KEY` | Credential explicitly enabled/licensed for HTTP Geocoder. Missing means coordinate fallback. Do not infer it from the public Maps key. |
| `YANDEX_GEOCODER_REFERER` | Optional HTTPS origin allowed by the key's domain restrictions, for example `https://dispatch.example`. The API sends its normalized origin plus `/` as the provider request's `Referer`. Credentials, paths, query strings, fragments, control characters and backslashes are rejected. Missing sends no Referer; invalid configuration disables lookups. |
| `YANDEX_GEOCODER_DAILY_LIMIT` | Confirmed positive integer allocation, at least 2. No assumed 1,000-request default. |
| `YANDEX_GEOCODER_QUOTA_TIMEZONE` | Explicit IANA timezone for the operator's confirmed quota day. Missing/invalid means fallback. |
| `YANDEX_GEOCODER_QUOTA_RESET_HOUR` | Local reset hour 0–23, default 0. This is an application policy setting, not a claim that Yandex resets at midnight in that timezone. Confirm the account's billing/reset period before enabling. |
| `YANDEX_GEOCODER_CACHE_SECONDS` | Optional address cache, 0 by default. Positive integer up to 300, enabled only when the deployment contract permits retention. |

Yandex states that the daily Geocoder counter resets at 00:00 Moscow time in its [official limit announcement and employee clarification](https://yandex.ru/blog/mapsapi/novyy-limit-zaprosov-dlya-geokodera). The isolated APK deployment plan uses a confirmed allocation of 1,000, `Europe/Moscow` and reset hour `0`, giving this app an 800-attempt ceiling. Read back the deployed variables before claiming activation. Keep shared development disabled when it uses the same provider key: separate application databases do not share the fleet counter and could overspend one vendor allowance.

All API instances must use the same quota policy. Keep timezone and reset hour stable during a quota day. The budget uses a monotonic local-day identifier and never replenishes on a backward day transition; restart, redeploy, key rotation and application rollback preserve counters. Missing or invalid configuration disables provider calls. Deployment must apply the additive migration before running the new API; it creates metadata tables and does not alter drivers, balances or region boundaries. Roll back application code first and retain these tables/counters when reverting.

The 2026-10-16 integration retest returned HTTP 403 without a Referer and HTTP 200 with an Ashgabat address when the same key received the allowed Railway web origin. This identifies a domain-restriction mismatch for that tested key. It does not mean every 403 has that cause. Set `YANDEX_GEOCODER_REFERER` to an origin already allowed by the selected key. The server uses this configuration only, never a caller-supplied Referer or the APK's `https://localhost` origin. No web or APK rebuild is required for this API configuration change.

A previous 403 may have opened the persistent one-hour breaker. A redeploy preserves it. Wait until it expires, or have the operator review and clear that breaker after confirming the corrected provider request succeeds. Keep the request counter and driver attempt timestamps intact.

## Retention and stale responses

With cache seconds 0, no provider address is written to PostgreSQL. Lookup-attempt coordinates and time, attempt purpose and per-installation convenience markers are retained for quota control, plus the fleet counter/breaker. An off-shift point in this budget metadata is not the shared driver tracking position. With licensed caching enabled, matching driver requests within 150 metres can reuse a cached address until expiry, with original lookup time preserved so cache hits cannot restart the five-minute display lifetime. Cache payloads are erased at startup and by a 60-second sweep after expiry, so the permitted retention window must include that cleanup delay. No expired payload is served. Ordinary Delete account archives the identity and keeps historical records. The deleted account is ineligible for new address lookups; cached provider payloads still expire through the same sweep. Only explicit isolated-environment maintenance resets remove the address-state rows.

The frontend retains the currently displayed address only in memory. It clears it on account changes, unusable GPS, movement of 150 metres or five minutes of age. A foreground address may survive hiding the app in memory only while it still describes the same fresh point; no address is persisted on the phone. Late replies cannot replace newer coordinates or another account. Backgrounding hides the label and pauses new requests; a still-fresh reply remains usable on returning to the same point. Foreground/reconnect catches up once when due on shift; it does not repeat the one-time convenience request off shift. GPS reporting remains separate.

The historical `GET /geo/reverse?lat=…&lng=…` contract remains available to dispatchers for order-map compatibility but returns `address: null`, coordinates and `reason: unavailable`, without spending provider quota. Drivers cannot use it to bypass fleet limits. Pickup/drop-off points and manually entered optional addresses still work. Paid order-map reverse lookups require separately scoped budget rules.

## Verification limits

Disposable-database HTTP tests cover street and microdistrict labels, nested district specificity, locality-only fallback, authorization, coordinate fallback, private credential handling, restricted-key Referer handling and invalid configuration, the five-minute gate without a movement requirement, races, the reserve, restart/instance persistence, day rollover, caching, provider errors and timeout. Browser tests use the real API/database and simulate only the external HTTP Geocoder. A driver-location regression checks that a microdistrict and house label appears without a street. Delayed real API responses verify stale-display rejection and concurrent-refresh protection. The release checks must cover one off-shift convenience attempt, the first Online refresh exception, five-minute foreground updates without movement, one due catch-up, background pause, cross-device limits and no dispatcher requests. Those checks do not establish physical Android timer or background survival. Automated tests do not verify a live vendor key, account entitlement, account reset timezone or physical Android background behavior. The live Referer retest above verifies only the tested key, origin and point; deployment still needs its own authenticated address check.
