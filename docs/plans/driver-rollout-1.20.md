## Order funding and lifecycle

Acceptance atomically checks sufficient available TMT, preserves the one-active-order rule and holds the accepted quote. `Balance.amount` and the driver's dashboard balance remain unchanged. Arrival through the existing `Ожидаю` action moves ACCEPTED to WAITING without a debit. Only the existing `Начать поездку` action, WAITING to STARTED, captures the held quote and records one PAYMENT. Completion must not charge again.

Use decimal arithmetic. Total means the existing `Balance.amount`; held means the sum of active holds; available equals total minus held. An exact available quote is sufficient. For example, total 100 and a 40 TMT acceptance produce total 100, held 40 and available 60. Arrival changes none of these. Start produces total 60, held 0 and available 60 with one 40 TMT payment. Cancellation before start produces total 100, held 0 and available 100 with no PAYMENT or REFUND.

The dispatcher balance UI shows total, held and available. Withdrawals and every negative adjustment reject attempts to spend held funds, including concurrent acceptance/adjustment requests. Positive adjustments retain existing limits and idempotency. All writers use a consistent lock order, currently driver, order where applicable, then wallet. Funding, order status and ledger writes commit together; publish events only after commit. Snapshot the accepted quote so later metadata edits cannot change the capture. Reservations alone create no hold. Inherited unpriced orders keep their existing positive-balance eligibility and zero-debit behavior.

| Actor/action                              | Allowed state                            | Result                                                                             |
| ----------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------------------- |
| Driver accept                             | Eligible unassigned public/private offer | ACCEPTED, one active assignment and quote hold                                     |
| Driver arrive                             | ACCEPTED                                 | WAITING, hold retained, no debit                                                   |
| Driver start                              | WAITING                                  | STARTED, hold captured once                                                        |
| Driver cancel                             | ACCEPTED, before arrival only            | CANCELLED requiring dispatcher action, release hold, no reason required            |
| Driver cancel after arrival               | WAITING or STARTED                       | Reject without changing order, assignment or money                                 |
| Dispatcher ordinary cancel                | NEW, ACCEPTED or WAITING                 | Terminal CANCELLED, release any hold, no debit/refund for the new hold flow        |
| Dispatcher ordinary cancel                | STARTED                                  | Reject; keep the existing separate audited resolution workflow                     |
| Dispatcher reoffer driver-cancelled order | CANCELLED requiring action               | Same order and order number become active NEW, fresh regional notification attempt |
| Dispatcher final cancel                   | CANCELLED requiring action               | Terminal CANCELLED, no remaining resolution actions                                |

Retries and simultaneous arrive/cancel, start/cancel, start/start, accept/accept and withdraw/accept requests must leave one valid result. Duplicate requests must not create another hold, capture, release, audit entry or offer attempt. Preserve shift-owner/session authorization, including the existing off-shift assigned-trip recovery policy. Logout, GPS loss and shift expiry must not cancel an assigned trip or discard its hold.

Preserve assignment and resolution history across cancellation and reoffer, including former driver, timestamps, actor, action and each accepted quote. Current assignment fields may clear on reoffer, but historical records must remain attributable. Historical ledger rows remain unchanged. Existing already-debited ACCEPTED/WAITING/STARTED orders need explicit compatibility handling so an upgrade cannot charge them twice or invent a second hold. Test this even though the authorized production reset clears operational records. An audited exceptional resolution must not silently bypass the new charge-at-start rule.

## Cancellation review and reoffer

Driver cancellation needs no reason form. The driver's cancel control appears only before marking arrival, and the API enforces that restriction independently. Cancellation frees the driver's current assignment and releases the hold. The dispatcher sees an actionable banner containing the human order number and driver identity, with a link to resolve that order.

The cancelled list puts unresolved driver cancellations first **before pagination**, with deterministic ordering within each priority group. Counts, filters, reconnect recovery and the banner use the same persisted action-required state. A terminal dispatcher cancellation has no Reoffer or Final cancel actions. Stale admin views must fail safely if another admin already resolved the item.

Reoffer uses the same UUID and human order number, original saved region and existing order details. It creates a fresh server-owned 20-second notification window, returns the order to active public work and clears stale assignment/lifecycle fields needed for a new claim. The former driver remains eligible under the usual account, shift, GPS and funds checks. Keep existing public semantics: every eligible region can claim immediately; only drivers in the original region receive the popup/native alert. Do not reuse `order:<id>` as notification identity. Each attempt needs its own identity shared by sockets, canonical inbox, polling, FCM and native deduplication. Invalidation of an old attempt must not silence a newer reoffer.

## Proposed API and event contracts

These names are proposals to refine before implementation, not claims about existing endpoints. Existing driver actions are under `/api/orders`; dispatcher actions are under `/api/admin`. Keep existing routes and fields compatible where possible. Unsupported/stale transitions return a stable conflict code and current state; UI visibility alone never authorizes an action.

- Retain `/orders/accept`, `/orders/private-offer/accept`, `/orders/waiting`, `/orders/start`, `/orders/complete` and `/orders/cancel`. Cancel accepts order identity with no required reason. Start returns authoritative order/funding data. Retry identity must survive network retry without authorizing a new lifecycle attempt.
- Add decimal-compatible balance fields `{ amount, heldAmount, availableAmount, currency: "TMT" }` to dispatcher reads and `balance:updated`. Existing `amount` stays total. Acceptance/release emit updates even when total is unchanged. Driver dashboard continues displaying `amount`.
- Add an immutable funding record per accepted assignment with quote, hold state and capture/release timestamps, plus durable uniqueness preventing duplicate capture. Model an assignment/dispatch attempt explicitly so the same order can be accepted again after reoffer without reusing financial or notification keys.
- Extend order DTOs with persisted resolution state such as `actionRequired`, `cancelledByRole`, previous driver summary, revision and `offerAttemptId`. Do not expose private driver/customer data in public offer payloads. Use a dedicated action-required priority in `/admin/orders?status=cancelled` before applying offset/cursor and limit. Supply an authoritative unresolved count/list for banner recovery.
- Propose `POST /admin/orders/:id/reoffer` and `POST /admin/orders/:id/final-cancel` for unresolved driver cancellations. Include expected revision and idempotency key. Ordinary dispatcher cancel stays `/admin/orders/:id/cancel`; existing permission checks apply to all three routes.
- Preserve existing `order:new`, `order:available`, `order:accepted`, `order:taken`, `order:waiting`, `order:started`, `order:cancelled`, `order:updated` and `balance:updated` responsibilities. Include order revision/attempt identity where consumers need to reject stale events. An action-required cancellation event must carry order number and authorized driver summary for admins; terminal resolution removes the banner across tabs.
- Canonical notification envelope should carry `{ id, channel, orderId, orderNumber, offerAttemptId, expiresAt, serverNow }` for an offer. A proposed event identity is `order:<orderId>:<attemptId>`; private offers need the same attempt distinction. The ID must match outbox, `/driver/notifications/ack`, native `/event` verification, native inbox, FCM and sockets. Revalidate expiry, current attempt, shift owner and credentials server-side. Delayed verification of an obsolete attempt rejects it. Clearing alerts targets attempt IDs rather than every event for an order.
- Remove stored mute as an eligibility gate. Retain compatible registration/capability rotation during transition from 1.19; do not let an old `enabled:false` disable a 1.20 installation. Keep installation/token authentication and session revocation checks.
- Propose explicit broadcast history pagination, either `GET /admin/messages/broadcasts` or a documented scope on the existing message route. Individual thread DTOs include `isBroadcast` and stable broadcast identity. Driver history and notification queries apply `sentAt >= user.createdAt`; private replies require the authorized driver identity. Read cursors must handle the merged chronology without marking another driver's private messages read.
